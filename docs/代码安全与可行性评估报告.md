## 1. 执行摘要

本次评估对 `Pay_zfb` 模块的 6 个 Java 文件做了全量审计，共发现 **20 项问题**，其中：

| 严重级别 | 数量 | 说明 |
| --- | --- | --- |
| 🔴 P0 严重 | 8 | 凭据已泄露、可直接造成资损、可越权入账 |
| 🟠 P1 高 | 4 | 验签配置错误、并发缺陷、注入模式、异常吞没 |
| 🟡 P2 中 | 8 | 工程可行性硬伤与代码质量问题 |

### 三条核心结论

**结论一：存在可直接刷单的越权入账漏洞，无需任何认证。**
全模块零鉴权（无登录态、无 Filter、无权限判断）。查询接口 `doGet` 在**不校验支付状态**的前提下调用入账，且**入账对象由 URL 参数指定**。攻击者自助下单后不付款，直接请求一个 GET 即可白拿额度。详见 [SEC-003](#sec-003)、[SEC-004](#sec-004)。

**结论二：支付宝应用私钥（2048 位 RSA）明文硬编码在 6 处，应视为已泄露。**
私钥、`appid`、服务商 `pid` 三者齐备，足以冒充该商户调用支付宝开放平台接口。已通过 DER 解析确认其为结构完整、未加密的 PKCS#8 私钥。**必须立即在支付宝开放平台重置密钥**——删除文件不解决问题。详见 [SEC-001](#sec-001)。

**结论三：本项目不具备继续开发的技术基础，建议重写而非改造。**
缺少构建文件、缺少全部依赖、`web.xml` 声明了 2 个不存在的 Servlet、回调依赖仓库外的 JSP。技术栈（Servlet 2.5 + 裸 JDBC）与团队现有 Spring Boot 3 体系不兼容，改造成本高于重写。详见第 6 章。

## 4. 详细发现

### 4.1 🔴 P0 严重问题

---

<a id="sec-001"></a>
#### SEC-001　支付宝应用私钥明文硬编码（最严重）

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb.java:28,73`、`zfb_cx.java:27,82`、`zfb_close.java:27,70`（共 6 处） |
| 级别 | 🔴 P0 严重 |
| 类型 | 凭据泄露（CWE-798 硬编码凭据） |

**证据**

变量 `ss` 被赋值为一段 Base64 字符串，直接作为 `DefaultAlipayClient` 构造函数的 `privateKey` 参数：

```java
String ss = "<PKCS#8 私钥 Base64，DER 1216 字节>";   // 商户应用私钥（2048 位 RSA）
String gs = "<SPKI 公钥 Base64，DER 294 字节>";      // 公钥材料

// 原代码中二者均为单行长 Base64 字面量，直接作为 privateKey / alipayPublicKey
// 实参传入 DefaultAlipayClient 构造函数。密钥本体已从本报告移除，
// 仅以模数指纹标识（见附录 8.1）。
AlipayClient alipayClient = new DefaultAlipayClient(url, appid, ss, "json", "utf-8", gs, "RSA2");
```

配套泄露信息：

| 项 | 值 |
| --- | --- |
| `appid` | `2017**********97`（已脱敏） |
| `sys_service_provider_id` | `2088**********72`（服务商模式，已脱敏） |
| 私钥类型 | RSA 2048 位，PKCS#8，**未加密** |
| DER 长度 | 1216 字节 |
| **模数指纹** | **`SHA-256(模数) 前 16 位 = 3f03b3a4197aefd7`** |

> 报告中以模数指纹标识密钥，不复述密钥内容。工单引用时请使用该指纹。

**影响**

持有应用私钥 + `appid` 即可**以该商户身份**调用支付宝开放平台接口。可调用的接口范围取决于该应用开通的权限，通常包括：统一下单、交易查询、交易关闭；若开通了退款权限，还包括**退款**。由于是**服务商模式**，影响面可能涉及多个子商户。

**利用方式**

攻击者从代码中提取私钥后，使用官方 SDK 构造请求即可，无需接触本系统。

**修复建议**

1. **立即在支付宝开放平台重置应用密钥**（生成新密钥对，替换旧私钥）。这是唯一有效的止损手段。
2. 排查该 `appid` 近期调用记录，重点看交易查询、关闭、**退款**接口有无异常。
3. 密钥改为外部注入（环境变量 / KMS / 配置中心），**代码中零密钥**。
4. 在代码仓库加入密钥扫描（gitleaks / trufflehog）作为 CI 门禁。

<a id="sec-002"></a>
#### SEC-002　数据库明文口令硬编码

| 项 | 内容 |
| --- | --- |
| 位置 | `IpaymentDao.java:30-32` |
| 级别 | 🔴 P0 严重 |
| 类型 | 凭据泄露（CWE-798） |

**证据**

```java
conn = DriverManager.getConnection(
  "jdbc:sqlserver://192.168.x.x:9999;databaseName=<库名>",
  "<账号>", "<明文口令>");     // 口令与账号同名，属弱口令
```

**影响**

- 账号与口令同名，属弱口令，易被字典攻击。
- 连接串还跨库访问第二个业务库（`<库名>.dbo.[Right]`），泄露范围扩大。
- 数据库主机为内网地址，一旦内网被突破（钓鱼、VPN 失陷），可直接拖库。

**修复建议**

1. 立即轮换该数据库账号口令，改为强随机口令。
2. 确认该数据库端口未对非授信网络开放。
3. 连接信息外置到配置中心，按最小权限原则拆分账号（应用账号不应有第二个业务库的访问权）。

<a id="sec-003"></a>
#### SEC-003　入账接口零鉴权，且入账对象由请求方指定

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb_cx.java:57`、`zfb_close.java:100` |
| 级别 | 🔴 P0 严重 |
| 类型 | 越权（CWE-862 缺少授权）+ 信任外部输入（CWE-807） |

**证据**

```java
String JgResult = ipaymentDao.payment(
    jsonObject2.getString("out_trade_no"),
    jsonObject2.getString("total_amount"),
    request.getParameter("UserNo"),      // ← 直接取自 URL 参数
    request.getParameter("UserName"));   // ← 直接取自 URL 参数
```

这两个 Servlet 没有任何登录态校验，`UserNo` / `UserName` 完全由调用方决定。

值得注意的是，`IpaymentDao.java:63-73` 会尝试从 `Java_Order_History` 反查真实的 `UserNo` / `UserName` 来覆盖入参：

```java
String HistSql = "select B.UserNo,B.UserName from Java_Order_History A "
               + "inner join <库名>.dbo.[Right] B on A.userno = B.userno where HistoryID = ?";
...
while (HistRs.next()) { userno = ...; username = ...; }   // 查不到则不覆盖
```

说明作者**已经意识到外部传参不可信**，但把防护补在了 DAO 层，且**反查无结果时外部传参原样落库**。这是典型的"补在了错误的地方"——正确的做法是在入口拒绝无归属的请求。

**影响**

匿名攻击者可指定任意加盟商账号入账，也可为自己的账号凭空增加额度。

**修复建议**

1. 入账接口加服务端鉴权：校验登录态，且会话用户必须与订单归属一致。
2. **删除** `UserNo` / `UserName` 入参，用户身份一律从服务端会话或数据库订单记录获取。
3. DAO 层的反查逻辑保留为纵深防御，但不能作为唯一防线。

<a id="sec-004"></a>
#### SEC-004　入账未校验支付状态（可直接刷单）

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb_cx.java:47-57` |
| 级别 | 🔴 P0 严重 |
| 类型 | 业务流程绕过（CWE-841） |

**证据**

```java
if (jsonObject2.getString("code").equals("40004")) { ... }
else if (jsonObject2.getString("code").equals("10000")) {
    IpaymentDao ipaymentDao = new IpaymentDao();
    String JgResult = ipaymentDao.payment(...);   // ← 直接入账
}
```

**`code = 10000` 仅表示"接口调用成功"，不表示"用户已付款"。** 真实支付状态在 `trade_status` 字段，取值包括 `WAIT_BUYER_PAY`（等待付款）、`TRADE_SUCCESS`（支付成功）、`TRADE_FINISHED`（交易完结）、`TRADE_CLOSED`（交易关闭）。`doGet` 分支**完全没有读取 `trade_status`**。

对比同一文件 `doPost` 分支（`zfb_cx.java:112`）确实检查了 `TRADE_SUCCESS`，**但该分支不入账**。即：

| 方法 | 校验 `trade_status` | 执行入账 |
| --- | --- | --- |
| `doGet` | ❌ 不校验 | ✅ **入账** |
| `doPost` | ✅ 校验 | ❌ 不入账 |

**两个分支的能力恰好互补，形成一个完整的漏洞。**

**利用方式**

```
1. 攻击者调用 /servlet/zfb?HistoryID=自建单号&UnitPrice=0.01  → 生成一笔支付宝订单（不付款）
2. 调用 /servlet/zfb_cx?OrderID=自建单号&UserNo=自己&UserName=自己  （HTTP GET）
3. 支付宝查询返回 code=10000、trade_status=WAIT_BUYER_PAY
4. 系统执意入账 → 攻击者白拿额度
```

**修复建议**

入账前置条件严格化为：

```java
if ("10000".equals(code) && ("TRADE_SUCCESS".equals(tradeStatus)
                          || "TRADE_FINISHED".equals(tradeStatus))) { ... }
```

并且**不在查询接口里入账**——入账只应由异步通知（notify）驱动，查询接口仅用于主动对账补偿。

<a id="sec-005"></a>
#### SEC-005　关单成功后错误入账（业务逻辑颠倒）

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb_close.java:97-100`（另有 `:89` 的响应体 key 错误） |
| 级别 | 🔴 P0 严重 |
| 类型 | 业务逻辑缺陷 |

**证据（错误一：关单后入账）**

```java
else if (jsonObject2.getString("code").equals("10000")) {
    IpaymentDao ipaymentDao = new IpaymentDao();
    String JgResult = ipaymentDao.payment(...);   // ← 关单成功却给用户加额度
}
```

业务上完全相反：关单意味着交易取消，应**释放**已占用的额度，而非增加。

**证据（错误二：响应体 key 用错）**

```java
JSONObject jsonObject2 = JSON.parseObject(jsonObject.getString("alipay_trade_query_response"));
//                                                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
// 应为 alipay_trade_close_response
```

在**关单**响应里取**查询**响应体，该 key 不存在 → `getString` 返回 `null` → `JSON.parseObject(null)` 返回 `null` → `jsonObject2.getString("code")` **必然抛 NullPointerException**。

对比同文件 `doGet`（`:46`）使用的是正确的 `alipay_trade_close_response`。

**判定**

`zfb_close.java` 的 `doPost` 是从 `zfb_cx.java` 复制粘贴后只改了一半的产物：改了请求类型（`AlipayTradeCloseRequest`），但没改响应体 key，也没改后续业务逻辑。**该分支自上线起就 100% 报 500。**

**修复建议**

1. 关单分支**删除入账调用**，改为释放额度或仅记录状态。
2. 修正响应体 key 为 `alipay_trade_close_response`。
3. 消除 `doGet` / `doPost` 的重复实现，抽为单一服务方法。

<a id="sec-006"></a>
#### SEC-006　下单金额由客户端指定

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb.java:25`、`zfb.java:70` |
| 级别 | 🔴 P0 严重 |
| 类型 | 参数篡改（CWE-472） |

**证据**

```java
String out_trade_no = request.getParameter("HistoryID");
String total_amount = request.getParameter("UnitPrice");   // ← 金额来自 URL
...
"\"total_amount\":" + total_amount + ","                   // ← 直接透传给支付宝
```

金额与订单号**全部由客户端指定，未与本地订单记录做任何比对**。同时 `out_trade_no` 也没有归属校验，可指定他人订单号。

**影响**

加盟商用 `UnitPrice=0.01` 下单即可换取 10 件货的额度（`passback_params` 硬编码为 `jiamengbuhuo&shuliang=10`），**直接资损**。

**修复建议**

1. 服务端根据 `HistoryID` 查询本地订单，**以本地订单金额为准**下单。
2. 校验订单归属当前登录用户、且状态为"待支付"。
3. 回传 `passback_params` 时携带真实业务参数（当前为硬编码）。

#### SEC-007　异步通知验签缺失

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb.java:34`（notify_url 指向仓库外 JSP）；本仓库无任何接收通知的代码 |
| 级别 | 🔴 P0 严重 |
| 类型 | 签名验证缺失（CWE-347） |

**证据**

```java

```

三个 Servlet 均为**主动发起**请求（`pageExecute` / `execute`），仓库内**不存在**任何被动接收支付通知并验签的代码。真正的入账入口是仓库外的 `TrReZfbPay.jsp`。

3. 任一步失败都必须记录并拒绝，**不得**"验签失败也放行"。

#### SEC-008　回调走明文 HTTP，且 return_url 与 notify_url 混用

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb.java:33-34`、`zfb.java:78-79` |

3. 参数使用标准 URL 编码。

#### SEC-009　支付宝公钥配置错误（下单链路验签必然失败）

| 项 | 内容 |
| --- | --- |
| 位置 | `zfb.java:29`（对比 `zfb_cx.java:28`、`zfb_close.java:28`） |
| 级别 | 🟠 P1 高 |

**验证方法与结果**

对三份 Base64 密钥材料做 DER 解析并提取 RSA 模数，比对指纹：

| 模数指纹（SHA-256 前 16 位） | 出现位置 | 判定身份 |
| --- | --- | --- |
| `3f03b3a4197aefd7` | `ss`（3 个文件的私钥）+ **`zfb.java` 的 `gs`** | 商户**自己的**密钥对 |
| `c94a1e024439f439` | `zfb_cx.java`、`zfb_close.java` 的 `gs` | 另一把公钥（应为支付宝公钥） |

**`zfb.java` 传给 SDK 的"支付宝公钥"（`gs`）与 `ss` 的模数完全一致，即商户自己的公钥，不是支付宝公钥。**

**影响**

- 下单链路用错误的公钥验支付宝响应签名 → 验签必然失败。
- `zfb.java:54-57` 捕获 `AlipayApiException` 后仅打印堆栈，`form` 保持空串 → 用户看到**空白页面**，且无任何错误提示。
- 三处公钥配置不一致（两把不同公钥），至少两处是错的，说明密钥管理完全失控。

**修复建议**

统一从配置读取支付宝公钥（**平台公钥**或**公钥证书模式**），删除代码中的所有硬编码密钥材料。

#### SEC-010　主键生成存在并发缺陷

| 项 | 内容 |
| --- | --- |
| 位置 | `IpaymentDao.java:46-61` |
| 级别 | 🟠 P1 高 |

**证据**

```java
String sql = "select max(DID)DID from TblGetAdvance where DID like '" + dfFormat.format(date) + "%'";
```

**影响**

1. **读-改-写竞态**：两个并发请求读到同一个 `max(DID)`，生成相同主键 → 插入冲突或数据错乱。无锁、无序列、无重试。

**修复建议**

改用数据库序列、`UUID`/`ULID`，或 `TblGetAdvance` 上的 `IDENTITY` 自增列；同时为业务键（`memory` 字段）加唯一索引。
